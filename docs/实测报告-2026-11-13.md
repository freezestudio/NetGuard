# NetGuard 实测报告（2026-11-13）

> 目标：验证“默认拒绝一切出网流量，只放行指定程序 → 指定地址:端口”是否真实成立。
> 环境：宿主 Windows 11 + Hyper-V；客户机 Windows 7 SP1 x64、Windows 10 22H2、Windows 11 24H2。
> 被测构建：`build\NetGuard.exe`（2026-11-12 14:45，`_WIN32_WINNT=0x0601`，静态 CRT）。

## 一、结论摘要

| 平台 | 默认拒绝 | 程序×地址×端口白名单 | 未列程序 | 未列目标 | 结论 |
|---|---|---|---|---|---|
| Windows 10 22H2 x64 | ✅ | ✅ 仅 allow.exe → 8.8.8.8:53/TCP | ✅ 全部拦截 | ✅ 全部拦截 | **核心目标成立（TCP/UDP/ICMP/DNS）** |
| Windows 7 SP1 x64 | ✅ 6 条过滤器 | ✅ 仅 NetGuard.exe → 8.8.8.8:53/TCP | ✅ ngcopy.exe 0 泄漏 | ✅ 其余 4 个目标 0ms 拦截 | **核心目标成立（TCP）** |
| Windows 11 24H2 x64 | ✅ 6 条过滤器 | ✅ 驱动+HASH → 8.8.8.8:53/TCP | ✅ curl/ping 被拦 | ✅ 其它目标 exit=7 | **核心目标成立（含驱动）** |

同时确认：

- 同一二进制**改名**、复制到**其他目录**，都不再被放行（白名单绑定的是文件路径/AppID）。
- 已允许程序访问**其他地址/其他端口**被拦截。
- 已建立 TCP 连接在策略下发后被重置；UDP、ICMP、DNS 在策略下发后均无法出网。
- 服务停止/崩溃/试用到期时过滤器消失（fail-open），这是现有“失败即安全”设计。

但存在若干**可被本地标准用户利用的绕过点**，见第四节；其中“程序目录可写 + 30 秒哈希巡检窗口”是生产部署前必须修的。

### 2.5 程序目录 ACL

```
C:\NetGuard BUILTIN\Administrators:(I)(OI)(CI)(F)
            NT AUTHORITY\SYSTEM:(I)(OI)(CI)(F)
            BUILTIN\Users:(I)(OI)(CI)(RX)
            NT AUTHORITY\Authenticated Users:(I)(M)
            NT AUTHORITY\Authenticated Users:(I)(OI)(CI)(IO)(M)
```

- 使用受限令牌（`runas /trustlevel:0x20000`）成功写入 `C:\NetGuard\stdwrite.txt`。

### 2.6 LanAllow 配置洞

- 策略 `LanAllow=8.8.8.0/24` 下发后，未列程序 `deny.exe` 可以访问 8.8.8.8:53（`exit=35`）；
  1.1.1.1:443 仍被拦截。
- `LanAllow` 是**任意进程、任意端口**放行整个网段；`initpolicy` 默认带 `LanAllow=192.168.1.0/24`。
- 如果门店 LAN 里有路由器/代理可出公网，任意程序都能借道。
- 默认样例里的 `[ep.2] 门店打印机 192.168.1.50:9100` 也因此不提供“按程序”限制。

## 四、残余风险与修复建议（按优先级）

### P0：程序目录可写 + 哈希巡检窗口

**风险**：标准用户替换 `C:\NetGuard\<业务程序>.exe`，在 30 秒巡检前用它连业务地址。
这直接破坏“只有指定程序可以联网”。

**修复**：

1. 安装/升级时加固程序目录（和业务程序目录）：
   ```powershell
   icacls C:\NetGuard /inheritance:r
   icacls C:\NetGuard /grant "*S-1-5-18:(OI)(CI)F"
   icacls C:\NetGuard /grant "*S-1-5-32-544:(OI)(CI)F"
   icacls C:\NetGuard /grant "*S-1-5-32-545:(OI)(CI)RX"
   ```
2. 把白名单程序放到普通用户不可写的目录（Program Files / ProgramData 受保护子目录）。
3. 更彻底：在 WFP callout 驱动里做连接时哈希/签名校验，而不是 30 秒巡检；
   或结合 WDAC/AppLocker 只允许签名程序运行。
4. 回归里增加“标准用户写入程序目录必须失败”的检查。

### P1：哈希巡检不是连接时校验

- 现状：`ALE_APP_ID` 只绑定路径；SHA-256 由看门狗每 30 秒检查。
- 影响：替换后最多 30 秒可用；服务未运行时没有巡检。
- 修复：callout 驱动连接时校验；或对业务程序做代码签名 + WDAC；
  或缩短巡检间隔（只能缩小窗口，不能根治）。

### P1：LanAllow 任意进程/任意端口

- 默认 `initpolicy` 带 `LanAllow=192.168.1.0/24`，任意程序可访问整个 LAN。
- 如果 LAN 内有代理/路由器可出公网，等于绕过“只有指定程序”。
- 修复：删除 `LanAllow`；对打印机等 LAN 目标使用 `[ep]` + `[proc]` 绑定；
  或给 LAN permit 也加 `ALE_APP_ID`。

### P2：空哈希 / `Path=*`

- `Validate` 允许 `Sha256` 为空；`VerifyHashes` 对空哈希直接跳过。
- `Path=*` 会生成不带 AppID 的 permit（任意进程）。
- 修复：生产模式要求 enabled proc 必须有 64 位 SHA-256；禁止 `*`；
  UI 保存时强制计算哈希。

### P2：fail-open 设计

- 服务停止/崩溃、试用到期 → 过滤器消失，终端恢复联网。
- 好处：不会把门店留在永久断网；坏处：管控可被“让服务不运行”绕过（需要管理员）。
- 建议：提供“失败即拒绝”的部署选项（持久化过滤器或内核驱动）；
  Win7 用户态无法建持久化 sublayer，强一致需要驱动。

### P3：IPv6 业务白名单（已修复）

- 原问题：`Cidr` 只支持 IPv4；默认拒绝覆盖 V6，但业务规则不能放行 V6 目标。
- 2026-11-13 已扩展 `Cidr` 支持 IPv6（`2001:db8::10/128`），在
  `ALE_AUTH_CONNECT_V6` 生成进程×地址×端口 permit（见第六节）。

### P3：Windows 11 / 代码签名

- WFP API 与 Win10/7 相同；Win11 24H2 客户机已跑通用户态拦截 + 驱动安装/拦截/卸载。
- Win11 的 Smart App Control / AppLocker 可能拦截未签名 EXE；
  交付前必须代码签名。
- Win7 已停止支持，长期建议迁移 Win10 LTSC/Win11。
- **仍未验证**：Secure Boot 开启 + HVCI 开启 + `testsigning off` 的生产加载路径，
  需要 EV/WHQL 正式签名驱动后再回归。

### 6.1 WFP callout 驱动原型（连接时哈希）

在安装 WDK 10.0.26100 后，新增 `drv/ngdrv.sys`，并接入用户态服务：

- 用户态 `src/ng_drv.cpp` 把策略中的启用程序（非 `*`、64 位哈希）
  通过 `\\.\NgDrv` 的 `IOCTL_NGDRV_SET_WHITELIST` 下发给驱动；
  服务侧用 `QueryDosDevice` 把 `C:\...` 转成 NT 路径
  `\Device\HarddiskVolumeX\...`；
- 驱动设备 DACL 仅 SYSTEM/Administrators；
- `PsSetCreateProcessNotifyRoutine` + `SeLocateProcessImageName` 在进程创建时
  按完整 NT 路径匹配白名单，先以 `Verified=FALSE` 入表（fail-closed），
  再计算 SHA-256 更新结果；
- `ALE_AUTH_CONNECT_V4/V6` callout 在连接时按 PID 查表：
  未验证 → `FWP_ACTION_BLOCK`，已验证 → `FWP_ACTION_CONTINUE`；
- 驱动 filter 权重 `0x7000`，可覆盖用户态 NetGuard 的业务 permit（`0x2000`）；
- 回滚/临时放行/服务停止时服务下发 `CLEAR`，避免残留误拦。

Win10 22H2 实测（用户态策略允许 `C:\NetGuard\ngblock.exe -> 8.8.8.8:53`）：

```text
service ready=True, ngdrv RUNNING
netguard apply: OK filters=6
ng.log: drv: 已下发 1 条白名单

正确哈希:      curl exit = 35   ← 驱动 CONTINUE + 用户态 permit 放行
追加字节篡改:  curl exit = 7    ← 驱动 BLOCK，覆盖用户态 permit
cleanup: OK filters=0
```

这证明“服务下发 + 连接时哈希门禁”链路可用，把原来 3 秒的替换窗口
压到进程创建时。安装/卸载已接入 `install-netguard.ps1 -InstallDriver` /
`uninstall-netguard.ps1`。

**Win7 SP1 x64 补充实测**（SHA-1 测试签名 + testsigning + `SUBSYSTEM:NATIVE,6.01`）：

```text
testsigning Yes, ngdrv RUNNING, LastStep=ok
正确哈希: 8.8.8.8:53 CONNECTED；114.114.114.114/1.1.1.1/Baidu 均 BLOCK
篡改后:   8.8.8.8:53 BLOCK；RESULT: all blocked = PASS
```

同时修正了一个关键语义：驱动 filter 必须用
`FWP_ACTION_CALLOUT_UNKNOWN`（而不是 `TERMINATING`），否则已验证进程返回
`CONTINUE` 会被当成最终动作，绕过用户态默认拒绝（Win7 上表现为
`114.114.114.114:53` 泄漏）。

以及在 Secure Boot + HVCI 开启、`testsigning off` 的 Win11 生产环境回归。
详见 `drv/README.md`、`lab/ngdrv-test.log`、`lab/win7-drv-result.txt`、
`lab/installer-driver-test.log`、`lab/win11-installer-driver-test.log`。

### 6.2 免费模式（无驱动/无证书）

按“不买 EV、不装驱动”的落地建议，新增 `free-mode.ps1`：

- Windows 防火墙出站默认阻止（Domain/Private/Public）；
- 按 `policy.ini` 生成“程序 × 远程地址 × 远程端口 × 协议”放行规则；
- 关闭 Windows 自带出站放行规则（Win10 182 条 / Win11 206 条，按机器不同）；
- DHCP 自动放行，DNS 默认禁止（可按 `AllowDnsServer` 放行）；
- 程序目录 ACL + 用户态 5 秒快检/30 秒全量哈希；
- 状态记录在 `%ProgramData%\NetGuard\freemode-state.json`，卸载时完整恢复；
- AppLocker 为实验性开关：本机 Win10 22H2 的本地策略 `FileHashRule` 会导致
  整个 Exe 集合不编译（fail-open），因此默认不使用。

实测：

| 平台 | 结果 | 日志 |
|---|---|---|
| Win10 22H2 x64 | **22/22** | `lab/free-mode-test-win10.log` |
| Win11 24H2 x64 | **22/22** | `lab/free-mode-test-win11.log` |

覆盖：默认 Block、规则生成、白名单放行、其他目标/未白名单程序/复制改名程序拦截、
管理程序可运行、卸载后规则清零/默认 Allow/系统规则恢复/网络恢复。

局限：对本地管理员无效；无连接瞬间哈希；会断开系统更新/商店/时间同步。
详见 `docs/免费模式.md`。
